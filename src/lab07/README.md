# ЛР7 Поиск сортировки и измерение времени

## Состав и запуск

`search.py`: linear_search, binary_search, two_sum_brute, two_sum_fast. `sorting.py`: bubble_sort, insertion_sort, selection_sort. `check.py`: проверка против эталонов. `bench.py`: замеры через timeit и таблица CSV. `bench_worker.py`: отдельный запуск большой сортировки с ограничением времени основным скриптом. `test_cases.py`: регрессии проверок и бенчмарка.

Запуск из корня `python_labs`:

```powershell
python -m src.lab07.check
python -m src.lab07.test_cases
python -m src.lab07.bench --quick
python -m src.lab07.bench
```

Быстрый режим сохраняет `data/lab07/bench_quick.csv` и не затирает [полный результат](../../data/lab07/bench.csv). Путь можно задать `--output PATH`.

## Алгоритмы и контракт

| Алгоритм | Принцип | Время | Дополнительная память |
|---|---|---|---|
| linear_search | Слева направо до совпадения | O(n) худшее | O(1) |
| binary_search | Уменьшение упорядоченного диапазона вдвое | O(log n) худшее | O(1) |
| two_sum_brute | Все пары i < j | O(n²) худшее | O(1) |
| two_sum_fast | Дополнение в словаре прошлых значений | Ожидаемое O(n), худшее O(n²) при плохих коллизиях | O(n) |
| bubble_sort | Соседние обмены, максимум вправо | O(n²), лучший O(n) с ранним выходом | O(n) с копией |
| insertion_sort | Вставка в отсортированный префикс | O(n²), лучший O(n) | O(n) с копией |
| selection_sort | Минимум оставшейся части | O(n²) | O(n) с копией |

Linear возвращает первое вхождение, binary — любое, отсутствие — −1. Binary требует уже отсортированный список; на другом входе результат не определён. Two Sum возвращает пару разных индексов либо None, при нескольких решениях допустимо любое. Все три сортировки возвращают новый список, исходный не изменяют. Внутри ручных сортировок нет sorted/sort/min/max; sorted используется как эталон и конкурент в замерах.

## Проверка корректности

Доступны `check_sorting(fn, trials=100)`, `check_search()`, `check_two_sum(trials=100)`. При успехе возвращают None; при ошибке assert содержит функцию, вход и результат. Случайные списки имеют длину 0…50, значения −100…100; seed фиксирован. Отдельно проверяются пустые и единичные входы, повторы, отрицательные, готовый и обратный порядок. Для binary проверяются крайние элементы и отсутствующие значения.

Фактический вывод:

```text
OK: 537 наборов (324 сортировки, 106 поиска, 107 Two Sum)
```

537 — число наборов: 324 вызова сортировок, 106 списков поиска и 107 задач Two Sum. Один набор поиска может содержать несколько запросов. Расхождений не обнаружено. Повторный вызов main и отклонённая ошибочная сортировка не изменяют глобальные примеры. Регрессионные проверки: **6 тестов, OK**. Не запускать проверки с `python -O`, который отключает assert.

## Методика бенчмарка

Измеряется один вызов через `timeit.timeit(..., number=1)`, секунды не включают генерацию входа и печать. Конкурирующие реализации получают одинаковые данные. Их копирование внутри сортировки входит в замер, поскольку одинаково требуется контрактом.

В обычном режиме сортировки проверяются на 1000/10000/100000 элементах, Two Sum — на 1000/10000. Для Two Sum единственная пара −1 и −2 находится в конце перемешанного списка положительных чисел; цель −3. Поиск: **10000 одинаковых запросов к 100000 элементам**. Цена sorted записана отдельно как search_prepare; время бинарного поиска не включает её повторно. Для поиска используется готовый упорядоченный список, а цена его подготовки измеряется отдельным эквивалентным вызовом sorted.

Три квадратичные сортировки на 100000 реально запускаются в отдельном процессе. `subprocess.run(..., timeout=60)` прекращает этот запуск по лимиту. Файл с числами читается до timeit внутри worker; успешный числовой результат — время самой сортировки. **Метка `>60s` означает превышение 60-секундного лимита всего дочернего процесса, не точный замер сортировки.** Это реальное наблюдение, не прогноз по формуле. Для защиты основной алгоритмический код остаётся обычным: ограничение находится только в драйвере измерений.

## Выводы

При росте n с 1000 до 10000 пузырёк замедлился с 0.027003 до 2.894171 с, примерно в 107.2 раза. Это согласуется с квадратичным ростом: увеличение размера в 10 раз даёт порядок ×100. Встроенная sorted выросла с 0.000079 до 0.001091 с, примерно в 13.8 раза: ближе к n log n, а не n². Вставки и выбор тоже квадратичны в общем случае; на 100000 все три учебные сортировки превысили установленный лимит процесса, что отмечено >60s без выдуманного точного времени.

Для 10000 запросов линейный поиск занял 45.742224 с; бинарный — 0.058875 с, подготовка sorted — 0.036496 с. С учётом подготовки получается 0.095371 с против 45.742224 с на этом прогоне. При одном запросе предварительная сортировка может быть дороже линейного поиска; при большом числе запросов её цена распределяется. Сравниваются O(qn) и O(n log n + q log n). На неотсортированном входе binary не гарантирует правильный ответ.

Проверка `check.py` прошла на 537 наборах без расхождений. Один замер не является универсальной константой: время зависит от входа, компьютера и нагрузки. Повторяемый seed фиксирует данные, а не секунды.

## Короткие ответы для защиты

**Почему две пары Two Sum могут различаться?** Решений может быть несколько. Проверяют корректность каждой пары — разные допустимые индексы и нужную сумму, — а не равенство двух ответов. Если решения нет, оба алгоритма должны вернуть None.

**Почему память сортировки O(n), хотя перестановки требуют O(1)?** Создаётся копия из n элементов. Сам алгоритм использует O(1) рабочей памяти сверх неё, но общая дополнительная память с копией — O(n). Число вложенных циклов определяет время, а не автоматически память.

**Почему бинарный поиск не всегда выгоднее?** Для q запросов линейный стоит O(qn), подготовка и бинарные — O(n log n + q log n). Стоимость сортировки окупается при повторных запросах; если данные уже отсортированы, подготовки нет.
